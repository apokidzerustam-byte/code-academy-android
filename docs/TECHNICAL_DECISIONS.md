## Этап 10: полировка и релиз (2026-11-22)
- **Режимы производительности** (`PerfPolicy`) влияют только на нейросетевого наставника — единственного тяжёлого потребителя CPU/RAM/батареи.
  Экономичный: 2 потока генерации/3 разбора запроса, без предзагрузки, выгрузка модели через 2 минуты, ответы на 30 % короче; стандартный — прежнее
  поведение (4/6 потоков, 10 минут, длина без изменений); расширенный — 30 минут и ответы на 30 % длиннее. Режим не поднимает число потоков выше
  подобранного по быстрым ядрам (`CpuTopology`). Смена режима перезагружает модель (потоки задаются при загрузке). Режим передаётся процессу `:mentor`
  в каждом запросе (`KEY_PERF`), поэтому не нужно синхронизировать состояние между процессами.
- **Журнал сбоев** — собственный локальный файл (`files/logs/crash.log`, до 60 000 символов, старые записи уходят целиком), а не Firebase/Crashlytics:
  в приложении нет сети и нет сторонних сборщиков. Пишутся необработанные исключения всех процессов и гибель `:mentor`; ученик сам решает, кому показать.
  Нативный крэш (сигнал в llama.cpp) этим не ловится: процесс `:mentor` просто умирает, это видно по записи «процесс нейросети завершился».
- **Подпись релиза.** Релизный ключ берётся из переменных окружения (секреты GitHub) и только при сборке тега `v*`; обычные сборки `main` остаются на ключе прототипа,
  иначе канал `apk` у заказчика перестал бы обновляться поверх. Без секретов тег собирается на ключе прототипа, а релиз помечается Pre-release. Ключ не создаётся
  автоматически: секрет из workflow сохранить нельзя (токен Actions не пишет секреты), а артефакт с ключом в публичном репозитории был бы утечкой.
- **Релиз — только черновик.** Публикация необратима для людей, уже скачавших APK, поэтому её нажимает владелец (docs/RELEASE.md).
- **R8 не включён:** Chaquopy, Pyodide-мост, JNI и kotlinx.serialization требуют правил сохранения; в APK (79 МиБ по аудиту CI) код — classes*.dex 7,3 МиБ (9 %), остальное — контент и озвучка 23, Pyodide 11, Chaquopy 10, нативные библиотеки двух архитектур 22; выигрыш от R8 — единицы мегабайт, риск поломки велик.
- **Аудит APK** (`ci/audit_apk.py`) гоняется в каждой сборке, а не только при релизе: нарушения (сеть, экспортированные компоненты, debuggable, allowBackup) должны ловиться сразу.
- **Версия:** `0.10.0-mvp.<номер сборки>` для сборок `main`; сборка тега `v1.2.3` получает версию `1.2.3` (versionCode — по-прежнему номер запуска, поэтому возрастает).
- **Иконка** — вектор «</>» (адаптивная, с монохромным вариантом для Android 13+), оригинальная; сторонних изображений в приложении нет.
- **Lint** — отчёт в CI, не барьер: разбор замечаний — по приоритету (TODO).

## Постоянный ключ подписи прототипа (2026-11-18)
Проблема: GitHub Actions подписывал APK debug-ключом, который создаётся заново на каждой машине CI.
У каждой сборки был свой сертификат, и Android отказывался ставить новую версию поверх старой
(у заказчика осталась версия этапа 1, без «Проектов»). Решение: постоянный ключ `signing/prototype.keystore`
в репозитории и versionCode = номер сборки CI. Ключ публичный — подходит только для прототипа;
для магазина приложений будет отдельный секретный ключ.

## Анимированные уроки: рендер в приложении + аудио по сценам (2026-11-19)
- Урок не видеофайл: приложение рисует сцену по scenario.json, звук — отдельный AAC-файл на сцену.
  Плюсы: размер (~1,5 МБ на урок вместо десятков МБ видео), текст кода можно копировать, тёмная тема,
  крупный шрифт, перемотка по сценам. Кадр вычисляется из времени (LessonTimeline) — перемотка тривиальна.
- Время плеера берётся из позиции MediaPlayer текущей сцены, поэтому анимация не уходит от голоса.
  Без озвучки урок идёт по таймеру (≈70 мс на символ текста) с субтитрами.
- Действия сцены растягиваются на длину речи; точная привязка — поле cue (номер фразы).
  Деление на фразы одинаково в Python (narrate.py) и Kotlin (LessonTimeline.splitPhrases), это проверяет тест.
- Качество синтеза контролируется автоматически: каждую фразу распознаёт faster-whisper, при ошибке > 22 %
  фраза синтезируется заново (до 3 попыток). Сравнение идёт в общей латинской записи («принт» = print).
- Аудио коммитится workflow в main; пересинтез только изменённых сцен (хэш текста, записи голоса и настроек).

## Чёткость и ударения озвучки (2026-11-19)
- Русская часть Chatterbox обучена на тексте с ударениями от russian_text_stresser, но без этого пакета
  ударения молча пропускались. Теперь ударения ставятся явно: автоматически (russian_text_stresser,
  numpy<2 из-за spaCy 3.6), затем поверх — словарь курса content-pipeline/pronunciation.json и поле stress сцены.
  Встроенная расстановка в Chatterbox отключается, чтобы не было двойных знаков (инструмент портит уже
  размеченные слова).
- Латинские термины читаются по словарю (print → «принт», SyntaxError → «си́нтакс э́ррор»): модель с меткой
  языка ru плохо читает латиницу.
- Каждая фраза синтезируется в 3 вариантах; выбирается самый разборчивый: 2·CER − средняя уверенность
  распознавания (avg_logprob). Опорная запись чистится (срез гула, шумоподавление, нормализация громкости).
  Параметры: exaggeration 0,45, cfg_weight 0,5, temperature 0,65 (спокойнее и чётче, чем по умолчанию).
- Workflow «Stress probe» за пару минут показывает текст, который получит синтезатор, — ударения
  проверяются до долгого синтеза.


## ИИ-наставник: два уровня, модель не скачивается приложением (2026-11-22)
- У приложения нет разрешения INTERNET — это главная гарантия, что код ученика никуда не уходит и код ученика
  в режиме A не может выйти в сеть. Поэтому модель не скачивается приложением (DownloadManager тоже требует INTERNET):
  ученик скачивает GGUF в браузере, выбирает файл, приложение проверяет SHA-256 и копирует его в files/models.
  Принимаются только файлы из каталога (точное совпадение SHA-256) — подменённый или повреждённый файл
  не попадёт в парсер llama.cpp.
- Модели (каталог после сравнения, см. ниже): Qwen3-4B-Instruct-2507 Q4_K_M (2,5 ГБ), Qwen3-1.7B Q4_K_M (1,1 ГБ),
  Qwen2.5-Coder 1.5B (1,1 ГБ) и 0.5B (0,5 ГБ), все Apache-2.0. Движок — llama.cpp (MIT), CPU, контекст 4096,
  длина ответа по виду запроса (подсказка 140, разбор ошибки 200, тема 260 токенов).
- Модель работает в отдельном процессе `:mentor`: нехватка памяти или сбой в нативном коде не роняют приложение,
  а ответ даёт лёгкий режим.
- Лёгкий режим — основа, а не запасной вариант: все материалы курса уже проверены автором (подсказки, конспекты,
  частые ошибки), разбор ошибок по правилам точнее маленькой модели. Нейросеть добавляет объяснения своими словами.
- Решение не выдаётся по построению: эталон не передаётся модели; просьбы о решении модель не получает;
  любой текст наставника проходит `SolutionGuard`. Полное решение — только кнопкой «решение» под заданием
  после попытки (как и раньше); наставник не пересказывает подсказку, которая почти раскрывает решение.
- Отказ от FTS5/SQLite для поиска по конспектам: конспекты маленькие, BM25 в памяти строится за миллисекунды
  и одинаково работает в JVM-тестах и на телефоне.
- Проверка в CI: `mentor_cli` (то же ядро) + настоящая модель на Linux, провокации отправляются модели напрямую;
  на эмуляторе — та же модель через JNI в процессе `:mentor`, импорт файла с SHA-256 и счётчики трафика.

## Нейросетевой наставник: скорость и качество после проверки на телефоне (2026-11-22)
Жалоба после первой проверки на телефоне: «отвечает странно, 9–10 секунд». Причины и решения:
- **Время.** Запрос был длинным, а до конца генерации ученик видел только «Генерирую…». Решения: короче запрос
  (конспект только для объяснения темы, подсказка и ошибка без него; сокращены лимиты разделов); кэш начала запроса
  в нативном слое (общая часть промпта не пересчитывается; для моделей с рекуррентными слоями, как Qwen3.5, кэш
  невозможен — частичное удаление не поддерживается, делается полный сброс); потоки по быстрым ядрам (`CpuTopology`:
  частота ≥ 70 % от максимальной; раздельно для генерации — до 4 и разбора запроса — до 6); ответ лёгкого режима
  показывается сразу, пока модель считает, ответ модели — по законченным предложениям; модель держится в памяти
  10 минут (было 3), при нехватке памяти выгружается сразу.
- **Качество.** Модель 0.5B повторяла служебный текст запроса (в сравнении — 4–8 ответов из 20); у всех малых моделей
  встречались выдуманные ошибки и рассказ об «ученике» в третьем лице. Запрос переписан (обращение на «ты», «не повторяй
  разделы и правила», цель сформулирована для ответа ученику), оборванный ответ обрезается до законченного предложения.
  Главный рычаг — модель: в каталог добавлены Qwen3-4B-Instruct-2507 и Qwen3-1.7B.
- **Выбор моделей — по сравнению в CI** (workflow «Сравнение моделей наставника», одни и те же 5–8 заданий × «Объясни тему»,
  «Дай подсказку», «Почему ошибка?»): Qwen3-4B-Instruct-2507 отвечает по делу и без эха, но втрое медленнее малых;
  Qwen3.5-2B/4B (гибридная архитектура) на процессоре медленнее при разборе запроса и не поддерживают кэш начала запроса —
  не взяты; Qwen2.5-3B не рассматривалась (лицензия Qwen Research, не Apache). Оценка качества — чтение ответов автором, а не
  слепая оценка по шкале: это ориентир, не бенчмарк.
- **Qwen3-1.7B** «размышляет» перед ответом: к запросу добавляется пустой блок `<think></think>` (`ModelInfo.noThink`), а в ответе
  такие блоки вырезаются. Qwen3-4B-Instruct-2507 размышлений не имеет.
- **Ссылки на модели закреплены на ревизии репозитория** (`resolve/<commit>/…`): файл в `main` могут заменить, тогда SHA-256 в каталоге
  перестанет совпадать. CI качает именно эти ссылки и сверяет размер и SHA-256.
- **Защита:** строка решения, записанная иначе (в JS `return "Привет, " + name + "!"` вместо шаблонной строки), раньше проходила
  (модель 4B выдала её в подсказке); теперь фрагмент кода в ответе, содержащий все слова строки эталона (от трёх слов), блокируется.
